Deployment Recipes

Self-contained, runnable shell scripts that serve a model behind an OpenAI-compatible API on NVIDIA hardware. Recipes are the deployment layer for the reference architectures and solution templates in this repo.

Layout

recipes/<platform>/<server>/docker-<model-slug>.sh   # Docker recipe (vLLM or NIM)
recipes/<platform>/<server>/serve-<model-slug>.sh    # llama.cpp native recipe

Platforms: gb10, precision, gb300 · Servers: vllm.

Conventions

  • #!/usr/bin/env bash + set -euo pipefail.
  • --port PORT (or -p) CLI override, env-var fallback declared at top.
  • docker pull then docker run -d --restart unless-stopped (pre-clean the old container with docker rm -f); print the verify curl at the end.
  • GB10 (DGX Spark, aarch64): --gpus all --ipc=host --ulimit memlock=-1 --ulimit stack=67108864, mount ~/.cache/huggingface.

Readiness contract, health checks, monitoring (all recipes)

Every docker-*.sh now builds, monitors and waits before returning (shared code: lib/common.sh, lib/monitoring.sh):

  1. pull image, replace the old container, docker run -d --restart unless-stopped;
  2. start/refresh the shared tokenomics Prometheus + Grafana (see ../monitoring/);
  3. block until ready — container running, /health 200, served name in /v1/models, and a tiny completion succeeds — then print one machine-readable line:
READY {"ready":true,"container":"lightning-3.5-gb10","port":8000,"base_url":"http://localhost:8000/v1",
       "served_name":"nvidia/nemotron-3.5-lightning","models":[...],"seconds_to_ready":212,
       "max_model_len":200000,"client_max_output_tokens":16384,"client_prompt_budget_tokens":182592,
       "prometheus":"http://127.0.0.1:9090","grafana":"http://127.0.0.1:3000/d/deskside-tokenomics"}
Exit Meaning
0 ready
1 container died / crash-looping (last logs + known-cause hints are printed)
2 wait timeout (default 1800 s; --wait-timeout SEC)
3 usage error

Common flags on every recipe: --no-wait, --wait-timeout SEC, --no-monitoring, --dry-run (prints the exact docker commands, tokens redacted, changes nothing — also the safe way for an agent to preview a rollout). Env equivalents: DESKSIDE_WAIT, DESKSIDE_WAIT_TIMEOUT, DESKSIDE_MONITORING, DESKSIDE_DRY_RUN.

Per-recipe health assessment (field debugging; read-only except one tiny completion): each recipe has a sibling health-<model>.sh — host/driver/runtime/memory/disk → container (state, restarts, OOM, restart policy) → endpoint (/health, /v1/models, smoke completion, optional --tool-test structured tool call) → load/KV-cache → log-signature scan with fixes → monitoring. Exit 1 on any FAIL; --json for automation; --bundle [DIR] writes a token-redacted debug tarball.

recipes/precision/vllm/health-qwen3.8-flash-next-nvfp4.sh --json

Recommended deployments

Exactly one recommended recipe per model × platform × use-case set, chosen by best measured performance (ties broken by fewer moving parts). Use-cases: chat = aggregate throughput at high concurrency (200-in / 200-out sweep); agent = agentic long-context shape (ISL 60k / OSL 1k) at concurrency 20. Routed variants always run LiteLLM with --num_workers matched to the host's core allocation.
